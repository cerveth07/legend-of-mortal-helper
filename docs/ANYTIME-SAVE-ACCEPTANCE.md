当前结论：支持范围内的剧情台词、剧情选择、单挑多行动重启恢复及再次存读已通过真实游戏界面验证；普通原生存读和附档故障保护也已通过。不是对全部剧本、战斗和辅助开关的穷尽验证。

## 已确认并修复的问题

1. 剧情脚本入口应使用原生 `StartStoryScript`；`CurrentStoryScript` 不由原生保存逻辑写入。
2. `dynamic`、`json` 及 `package` 属于运行库。按实际模块定义和初始对象身份识别，不通过跳过所有自定义表来开放存档。
3. 剧情自有状态支持有界嵌套标量表；清理 MoonSharp 的删除墓碑，拒绝循环、别名、元表和不支持对象。原始全局 API 改绑或新增不支持对象也拒绝保存。
4. 插件自定义数组、列表改为显式有界附档编码，保留双精度及随机调用数据，不依赖实机可能遗漏字段的 Unity 序列化。
5. 原生加载后的场景初始化会覆盖资产型旗标；最终发布构建曾重现单挑首停点仅S9200不同。于剧情脚本入口或单挑原生Start协程执行前恢复原生开场 baseline 旗标，随后正常重放；最终仍核对完整目标，不忽略天气字段，也不按期望目标强制改值。
6. 原生旗标集合合法地重复引用同一资产。恢复按原生集合顺序及资产身份验证，冲突值仍拒绝。
7. 单挑行动点改为观察实际协程状态机完成；恢复后保留开场原生数据，供再次保存。
8. 战斗场景没有原生储存面板。补充明确的储存模式，复用编号列表，隐藏删除入口、确认覆盖，禁止误走原生读取，并在退出后恢复读取界面。
9. 事务提交或回退决定持久化后才清理备份；中断及持久化失败保留恢复材料。

## 自动检查与限制

常规构建包含文件事务故障注入、剧情附档、单挑附档以及保存菜单状态路由测试。独立 CLR 测试还使用实际游戏的 Fungus/MoonSharp 程序集验证 Lua 状态行为；这些检查与上表的实机证据分开计算。

旧实验附档可能已遗漏状态，不做猜测性修复；必须保留完整备份，格式不支持时明确拒绝。轮盘进行中、无法捕获的 Lua 状态、辅助改变战斗状态等位置仍拒绝创建随时存档。

最终插件SHA-256：`a8410b95c9548a036c66d870ecd29a7ccea959674229e719cfdbc685c524dcb6`（`diagnostics=false`）。构建445项检查、Python26项检查、实际Fungus/MoonSharp行为16项、游戏元数据合同14项通过；77个具名Harmony目标及协程目标解析通过。

本机完整日志、截图、测试副本及原始玩家存档哈希基线另存于工作区 `mortal-runtime-evidence`，不将游戏资产、原始存档或完整游戏程序集加入公开源码。关键证据：64/69/73/76及182/184最终DLL剧情闭环，145/148及186/188最终DLL选择恢复与分支，171/175/178/179最终单挑恢复、再次存读及结算，159普通原生冷读取，161/164/166/169附档故障与有效原生档恢复。

## 对此前失败的处理原则

先核实真实原生保存入口、运行库和序列化行为，再修改恢复逻辑；无法完整表达的状态明确拒绝，不以跳过字段换取成功。诊断构建通过后，仍以同一最终发布DLL反复冷启动复测；本轮正是在这一步重现并定位了S9200资产覆盖问题。旧档、失败材料与玩家原进度均保留，未用启动成功替代存读闭环。
