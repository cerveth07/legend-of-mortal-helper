# 存档槽事务设计

更新：2026-10-22。本文记录`随时存档`写入路径的独立设计。实现位于
[`src/Core/SlotTransaction.cs`](../src/Core/SlotTransaction.cs)、
[`src/Game/AnytimeNative.cs`](../src/Game/AnytimeNative.cs)、
[`src/Game/AnytimeStory.cs`](../src/Game/AnytimeStory.cs) 与
[`src/Game/AnytimeDuel.cs`](../src/Game/AnytimeDuel.cs)。验证结果见
[VALIDATION](VALIDATION.md)。

## 为什么需要它

原生存档文件由游戏写入，插件无法用"暂存—交换整个槽位"的方式独占提交。
一个编号槽在实验存档形态下由多个文件共同表达：

| 文件 | 含义 |
|---|---|
| `<槽>.dat` | 游戏原生存档，唯一被游戏读取的文件 |
| `<槽>.dat.mha` | 剧情附档：脚本起点、事件日志、随机状态、目标状态 |
| `<槽>.dat.mha-required` | 剧情附档为必需件的标记 |
| `<槽>.dat.mhduel` | 单挑附档：行动序列、随机带、停点摘要 |
| `<槽>.dat.mhduel-required` | 单挑附档为必需件的标记 |

修复前的两处缺陷都源于同一个错误推断：

1. **剧情回退按"备份文件是否存在"决定目标。** 备份不在时，代码认为槽位
   原本为空，于是删除原生档。备份可能因外部清理、杀毒、复制中断或前一次
   崩溃而缺失，此时删除的是玩家真实存档。
2. **普通原生档覆盖实验槽时先写原生、后删附档。** 两次操作之间崩溃，会留下
   与原生档哈希不匹配的旧附档；旧逻辑据"附档存在但校验失败"拒绝读取一个
   完整有效的原生存档。

两者的共同点是把**文件当前的存在性**当作**历史事实**。事务日志改为在写入前
记录历史事实，之后不再重新猜测。

## 日志格式

日志写在 `<槽>.dat.mhtx`，纯文本、逐行、路径与操作名以 Base64 编码，避免
分隔符与编码问题。固定头部 `slot-transaction 1` 提供格式版本。

```
slot-transaction 1
op=<base64>              # story | duel | supersede
state=prepared           # prepared | committed | rolledback | broken
new=<base64 哈希 | ->     # 已校验替换文件的哈希，未记录时为 -
n=<条目数>
<序号>|<0|1 原本存在>|<base64 原始哈希|->|<base64 路径>|<base64 备份路径|->
```

每个参与文件一条记录。`原本存在`与`原始哈希`在**任何写入之前**采集，备份
副本写完后立即回读校验，不一致则整体放弃。备份文件名为 `<槽>.dat.mhtx.bN`。

## 状态机与提交边界

```
Begin ──► prepared ──(RecordReplacement + Commit)──► committed ──► Complete
             │                                                        ▲
             └──(Rollback 全部成功)──► rolledback ───────────────────┘
             └──(Rollback 部分失败 / 备份不可用)──► broken （保留全部材料）
```

- **提交边界是 `Commit()`**，且只在调用方已回读并校验新文件之后调用：剧情为
  `ReadRecord` 通过，单挑为双文件哈希与附档自校验通过，普通覆盖为原生文件
  与内存对象哈希一致。
- `RecordReplacement()` 先于 `Commit()` 写出已验证的替换哈希。这两个写入之间
  崩溃时，日志仍是 `prepared` 但已带可信哈希，下一次结算可以安全地"向前完成"。
- `prepared` 且无可信替换哈希时一律**回滚**。用户的存档操作从未得到确认，
  恢复保存前状态是可解释的结果。

## 结算规则

读档前（`SaveSystem.LoadGameData` 前缀）与写入前（`SaveGameData` 前缀）都会
对目标槽执行 `SettleSlot`：

| 读到状态 | 处理 |
|---|---|
| 无日志 | 不做任何事 |
| `committed` / `rolledback` | 清理日志与备份，结束 |
| `broken` | 拒绝读/写，报告日志路径，保留全部文件 |
| `prepared` + 替换哈希与当前原生文件一致 | 完成该操作的附档退役，清理 |
| `prepared` + 其他情况 | 回滚到记录的原始状态；失败则拒绝 |

已提交日志的"向前完成"只做附档退役——删除该形态不再需要的旧附档。原生档
本身不会被丢弃，因为它是记录中已验证的替换结果。

## 回滚的硬性规则

1. 先校验**全部**备份的哈希，任何一个不可用就**不写任何目标文件**，直接进入
   `broken`。这样"备份缺失"永远不会变成"删除目标"。
2. 恢复每个文件后立即回读校验；不一致即 `broken`。
3. `原本存在=否` 的条目才会删除目标文件——这是唯一允许删除的判据，因为它来自
   写入前的记录，而不是写入后的观察。
4. `broken` 保留日志、备份与中断标记。后续读档明确拒绝并给出路径，而不是
   宣称回退成功。

## 各种中断情形的结果

| 情形 | 磁盘结果 |
|---|---|
| 首次创建存档后失败 | 删除本次新建的原生档、附档与标记 |
| 覆盖已有档后原生写入失败 | 原生档与附档还原为写入前内容（哈希一致） |
| 原生写入成功、附档写入失败 | 同上，整对回滚 |
| 附档写入成功、提交前崩溃 | `prepared` → 下次回滚整对 |
| 提交后、清理前崩溃 | `committed` → 下次仅清理 |
| 备份复制失败 | `Begin` 抛错，未改动任何存档文件 |
| 日志写入失败 | `Begin` 抛错并删除已建备份 |
| 日志损坏 | 解析拒绝，槽位保持不可读，不猜测 |
| 回滚中途异常 | `broken`，保留材料，可重试 |
| 覆盖普通档时崩溃于清理前 | 已记录可信替换哈希 → 向前完成，旧附档退役 |

## 与旧行为的兼容

- `.mha-pending` 不再写出。上一版本留下的 `.mha-pending` 在原生档存在时仍会
  阻止写入与读取，提示玩家从备份恢复。
- `.mha-rollback` / `.mha.rollback` 单独保留且从不删除：在没有 `.dat` 时它们
  可能是玩家唯一的存档副本。读取不依赖它们，日志会提示不要手动删除。
- 附档与原生档哈希不匹配时，若 `<槽>.dat.mha-required` 仍在，视为不可判定的
  歧义并拒绝；若标记已不在，说明附档属于更早的存档，把它改名为 `.mha.stale`
  保留后按原生档载入，并在状态栏说明当前处于原生检查点而不是精确恢复点。
- 空槽位上的孤立附档会被清理，避免"—required 存在但附档缺失"永久阻塞该槽。
- 游戏删除槽位（`SaveSystem.DeleteSaveData`）后，其附档与事务日志一并清理。

## 已知局限

- 事务只覆盖**文件层**的提交与回退，不覆盖游戏内状态。状态正确性依赖回放与
  状态核对，两者是不同层次的证据。
- 若存档目录本身不可写，日志无法写入，槽位会保持不可读而不是降级为无事务写入。
- 未提交源码没有跨进程文件锁，同时运行两个游戏实例会造成竞争；游戏本身也不支持。
